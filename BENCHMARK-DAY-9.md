# День 9: сжатие истории

Обычный чат и агент с инструментами используют общую службу подготовки контекста. По умолчанию сжатие включено: `keep=6`, `batch=10`.

## Как устроено

1. Загружается сохранённая история диалога и отдельное summary из `ContextSummaries`.
2. Пока за пределами последних `keep` сообщений не накопится `batch` новых сообщений, используется прежнее summary и ещё не сжатый хвост.
3. Когда порог достигнут, текущая модель получает прежнее summary и только новую старую часть истории. Она создаёт обновлённую память: имена, даты, бюджеты, ограничения, решения, изменения договорённостей и значимые результаты инструментов.
4. Только завершённое непустое summary записывается вместе с границей покрытой истории. Ошибка API или обрезанный ответ не заменяют прежнюю память.
5. В основной запрос передаются системный промпт, summary, недавняя часть истории и текущий вопрос. Старые сообщения второй раз в этот запрос не добавляются. Если summary оказалось длиннее исходного контекста по локальной оценке, используется исходный контекст.

`keep` — минимальное число исходных сообщений, а не число пользовательских запросов. В паузе между сжатиями хвост длиннее: при обычных парах user/assistant с `keep=6`, `batch=10` он растёт до 14 сообщений, после следующего обновления возвращается к 6. Целый ход с вызовами инструментов никогда не разрывается, поэтому фактический хвост может быть больше заданного минимума.

Summary хранится отдельно от сообщений и восстанавливается при перезапуске. Полный исходный журнал остаётся в SQLite, чтобы можно было выключить сжатие и сравнить режимы. `/reset` очищает журнал и summary. Изменение `keep` сбрасывает границу памяти для пересборки по новой настройке. Сохранять прежнюю БД для этого учебного проекта не требуется: при первом запуске с новой схемой `DatabaseInitializer` пересоздаст старую базу.

## Управление из консоли

```text
/compression             показать настройки
/compression on          включить сжатие
/compression off         отправлять полную историю
/compression keep 6      минимум последних сообщений как есть, N >= 2
/compression batch 10    порог обновления, N >= 1
/compression now         обновить память, не дожидаясь batch
/summary                 посмотреть сохранённую память
/tokens                  токены ответов и отдельно расход сжатия
```

Отдельный запрос создания summary тоже расходует токены. После хода консоль показывает его usage, если обновление произошло именно на этом ходу. `/tokens` показывает накопленный расход всех обновлений. Существующая расчётная стоимость ответов не включает summary; benchmark сравнивает общий расход токенов, включая summary.

## Проверка памяти на реальной модели

```powershell
dotnet build --no-restore
dotnet run --no-build -- --benchmark day9
```

Нужны интернет и переменная окружения `PROXYAPI_API_KEY`. По умолчанию используется `openai/gpt-4o-mini` через ProxyAPI. `--no-build` пропускает только сборку: каждый запуск делает новые реальные запросы и получает новые ответы от API.

Обычный запуск последовательно показывает шесть этапов:

1. **Эталонные детали:** заранее фиксируются имя, срок, бюджет, ограничения и решения.
2. **Диалог:** 30 сообщений, включая реальные ответы модели. Видны время каждого запроса и токены API.
3. **Сжатие:** модель обновляет отдельное summary; показаны заменённые сообщения, размер контекста и последние сообщения как есть.
4. **Вопросы:** по каждой детали задаётся одинаковый вопрос без сжатия и со сжатием. Показаны эталон, оба ответа и usage.
5. **Сравнение:** количество верных деталей и расход токенов, включая все запросы создания summary.
6. **Вывод:** какие детали потерялись и окупилось ли сжатие в текущем прогоне.

Между этапами нажимайте **Enter**. Для запуска без пауз добавьте `--auto`. Все результаты записываются в один каталог `results/day9`; следующий запуск обновляет те же файлы.

Также поддерживаются `--provider`, `--base-url`, `--api-key-env`; справка — `--help`. Для модели с внутренними рассуждениями установленного лимита ответа может не хватить; такой запуск завершается с ошибкой, а не выдаёт обрезанный ответ за проверенную память.

До первого API-вызова записываются сценарий и эталонные детали. Затем модель участвует в диалоге из **30 сообщений: 15 пользовательских реплик и 15 ответов**. В первых репликах называются 13 деталей: название, имя, срок, бюджет, запрет облака, платформа, размер команды, база, каталог данных, пилотная группа, время напоминания, экспорт и решение о мобильной версии. В середине бюджет меняется с 480000 на 420000 рублей. Последние реплики отвлекают разговор на интерфейс и проверки, не повторяя ранние детали.

Созданный диалог используется в обоих режимах без изменений. Для режима сжатия он проигрывается по тем же границам ходов с обычными обновлениями summary; перед проверкой сжимается остаток старых сообщений. После этого задаются одинаковые вопросы по каждой детали. Ответы на проверочные вопросы не добавляются в контекст, чтобы не помогать следующему вопросу. Генератор summary не получает список эталонов или проверочных вопросов.

Обычно выполняются **44 API-вызова**: 15 для общего диалога, 3 для summary и 26 для вопросов. Создание общего диалога учитывается отдельно как одинаковая подготовка. В сравнении учитываются входные и выходные токены вопросов и **все три обновления summary**. Экономия измеряется для продолжения разговора из 13 независимых вопросов; на одном коротком вопросе затраты на summary могут ещё не окупиться.

Файлы в `results/day9`:

- `scenario.json` — детали, вопросы и эталонные варианты, зафиксированные до запуска;
- `transcript.json` — исходные 30 сообщений;
- `summary.json` — отдельная память, её граница и накопленный usage;
- `answers.json`, `answers.csv` — ответы обоих режимов по каждой детали;
- `report.json`, `report.md` — результаты, потерянные детали и расход токенов.

Автопроверка ищет эталонные факты в ответах после удаления пробелов и пунктуации, различает границы чисел (3 и 13), а ДА/НЕТ сравнивает целиком. Для экспорта должны присутствовать оба факта: CSV и UTF-8. Проверка лексическая и не заменяет ручную оценку: в отчёте сохранены все ответы. Один прогон не гарантирует сохранения всех возможных деталей в других разговорах. Повторно оценить уже сохранённые ответы без платных запросов: `dotnet run --no-restore -- --benchmark day9 --rescore results/day9`.

Актуальное сравнение, исходные ответы и вывод находятся в [results/day9/report.md](results/day9/report.md). Числа рассчитываются заново по фактическим ответам каждого запуска и не зафиксированы в инструкции.

## Офлайн-проверки реализации

```powershell
dotnet run --no-restore -- --benchmark day9 --self-test
```

Проверки используют настоящий SQLite в памяти и подставного AI-провайдера, без сети и платных вызовов. Проверяются порог сжатия, сохранение последних сообщений, накопительное summary, принудительное сжатие, восстановление после открытия нового DbContext, переключение режима, изменение `keep`, ошибки, отмена и обрезанный ответ, отказ от слишком длинного summary, целостность цепочки инструментов, интеграция обоих агентов, учёт usage и очистка summary вместе с историей.
