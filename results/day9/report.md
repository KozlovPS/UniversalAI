## Итоговое summary

Проект настольного планировщика «Кедр» инициирован. Заказчик и ответственный за приёмку — Марина Соколова. Приложение предназначено для небольшой мастерской, чтобы организовать заказы и распределить работу между сотрудниками. В настоящее время согласовываются требования.

Срок сдачи проекта установлен на 18 декабря 2026 года. Бюджет обновлён до 420000 рублей (ранее 480000 рублей), включая разработку, проверку и подготовку инструкции. Продукт должен быть простым и понятным для демонстрации заказчику без длинной презентации.

Приложение должно работать полностью офлайн, облачные сервисы и отправка данных наружу запрещены. Интернет в мастерской нестабилен, и сотрудники не хотят переносить внутренние заметки в сторонние системы. Авторизация не должна требовать внешнего сервера, и это требование не подлежит изменению.

Целевая платформа — Windows 11. В команде разработки 3 человека. У сотрудников обычные рабочие компьютеры с мышью и клавиатурой, сенсорный интерфейс не требуется. Основное окно должно открываться быстро и показывать необходимые действия без обучения. Сложная персонализация на первой версии не планируется.

Техническое решение принято: база данных — SQLite, рабочие данные будут храниться в каталоге D:\\Kedr\\Data. Изменения должны сохраняться сразу после редактирования карточки заказа, с отображением статуса сохранения в интерфейсе. Обсуждение других баз данных не требуется. Восстановление после аварийного закрытия будет проверено отдельным сценарием.

Для пилотной группы выделено 12 сотрудников. Ежедневное локальное напоминание должно появляться в 09:30, не блокируя доступ к списку заказов. Текст уведомления должен быть спокойным и коротким. Экспорт данных будет в формате CSV (UTF-8), мобильная версия исключена из первого релиза. Экспорт должен быть доступен из списка заказов, а путь сохранения выбирает пользователь. Особые интеграции с бухгалтерией пока только обсуждались и не входят в согласованный объём.

В карточке заказа должны быть название, описание, состояние и заметка исполнителя. Большое описание допустимо сворачивать. Расположение полей: название, состояние, описание (сворачиваемое), заметка исполнителя. Для списка заказов важна читаемость; цвет не должен быть единственным способом показать состояние. Рядом с меткой нужен короткий текст. Тестирование списка заказов будет проведено с участием сотрудников для оценки читаемости.

Обсуждены ошибки ввода: если обязательное поле пустое, объяснение нужно показывать рядом с ним. Введённый текст нельзя терять при закрытии предупреждения. Пользователю полезно видеть, как исправить ошибку, без технических кодов. Пример сообщения об ошибке: "Пожалуйста, заполните это обязательное поле."

Обсуждена инструкция для сотрудников: начать с повседневного действия, затем показать исправление опечатки и завершение заказа. Скриншоты можно добавить после стабилизации интерфейса. Название раздела про исправление данных: "Исправление данных заказа."
