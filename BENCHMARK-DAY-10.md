# День 10: запускаемый бенчмарк управления контекстом

Бенчмарк UniversalAI: три стратегии проходят один сценарий Дня 9, отвечают на одинаковые вопросы и сравниваются по памяти, токенам и размеру модулей. Отдельно проверяются checkpoint, две независимые ветки и переключение между ними. Ниже приведены инструкция запуска и расширенный тест-план.

## Быстрый запуск

Из корня репозитория:

```powershell
dotnet build --no-restore
dotnet run --no-build -- --benchmark day10 --self-test
dotnet run --no-build -- --benchmark day10 --auto
```

Последняя команда выполняет реальные платные вызовы. Нужны интернет и переменная окружения `PROXYAPI_API_KEY`. Модель по умолчанию — `openai/gpt-4o-mini` через ProxyAPI. На стандартных настройках: **202 API-вызова**, включая ветки. До запуска без `--auto` программа показывает условия и ждёт Enter. `--self-test` полностью офлайн: тестовая модель проверяет механику, её ответы не являются измерением качества памяти.

Варианты:

```powershell
# Сравнение трёх стратегий без веток: 70 платных вызовов
dotnet run --no-build -- --benchmark day10 --skip-branches --auto

# Новый общий диалог вместо сохранённого: дополнительно 15 вызовов
dotnet run --no-build -- --benchmark day10 --generate --auto

# Параметры модели, окна и каталога результатов
dotnet run --no-build -- --benchmark day10 --model openai/gpt-4o-mini --keep 6 --batch 10 --output results/day10/manual --auto

# Пересчитать сохранённый отчёт без API
dotnet run --no-build -- --benchmark day10 --rescore results/day10/manual
```

Также доступны `--transcript`, `--provider`, `--base-url`, `--api-key-env`, `--help`. По умолчанию берётся `results/day9/transcript.json`, проверяются число сообщений, роли и совпадение всех пользовательских реплик со сценарием Дня 9. Реальные контрольные ответы и память не загружаются из прежнего отчёта: они создаются новыми запросами.

Результаты сохраняются в новый каталог `results/day10/<UTC>/`: `report.md`, `report.json`, `answers.csv`, `scenario.json`, `transcript.json`, полные запросы `requests.jsonl`, результаты вызовов `calls.jsonl`, checkpoint и снимки A/B каждой стратегии. Вызовы веток и генерация общего диалога учитываются отдельно от основного сравнения. При сбое уже записанные запросы и ответы остаются на диске; `Complete=false` в частичном отчёте означает незавершённый запуск. Непустой `--output` отклоняется, чтобы результаты разных прогонов не смешивались.

Реализован тест A и эксперимент C: независимые вопросы, копии состояний, продолжение A/B, запись и восстановление веток с диска, проверка изоляции. Стратегии выбираются в `Day10ContextSession`, агенте бенчмарка. Summary вызывает исходный `ContextCompressionService` Дня 9 через SQLite. Обычный консольный чат и его команды этим изменением не расширены. Тест B ниже и часть дополнительных критериев служат планом дальнейшей интеграции в основной чат.

## 2. Условия эксперимента

1. Использовать одну модель, провайдера, системный промпт Дня 9, одинаковые лимиты ответа и `temperature=0`. Зафиксировать дату, модель, endpoint, параметры и идентификатор прогона. API-ключ не сохранять.
2. Для основного сравнения отключить инструменты: использовать прямого агента. Интеграцию с агентом инструментов проверить отдельно.
3. Основные настройки: `N=6` исходных сообщений истории, summary `batch=10`. N считает сообщения user/assistant, а не пары. System prompt, блок памяти и текущая реплика пользователя в N не входят.
4. Для Sliding Window и Sticky Facts отправлять последние `min(N, history.Count)` сообщений завершённой истории. Для summary сохранить алгоритм Дня 9: целые ходы, накопление batch, принудительное сжатие остатка перед финальными вопросами и отказ от summary, если оно длиннее исходной истории. Записывать фактическое число сообщений и факт использования summary.
5. Полный журнал можно хранить отдельно для воспроизведения и checkpoint. В Sliding Window он не должен попадать в активный контекст или скрытую память. Если реализация физически удаляет журнал, одинаковый сценарий подавать из внешней тестовой фикстуры.
6. Генератор памяти получает только сообщения и предыдущее состояние памяти. Эталонные ответы и проверочные вопросы ему не передавать.

Summary из Дня 9 иногда отправляет хвост длиннее N и может вернуться к полной истории. Это часть проверяемой реализации; такую строку отчёта нужно явно отметить, иначе сравнение будет вводить в заблуждение.

## 4. Тест A: сравнение на одинаковом диалоге

Цель — изолировать влияние памяти. Ответы исходного диалога одинаковы для всех стратегий, новые ответы модели генерируются только на контрольные вопросы и при обновлении памяти.

Для каждой стратегии создать отдельное чистое состояние и последовательно проиграть 15 ходов общей фикстуры:

1. Передать очередную пользовательскую реплику обработчику выбранной стратегии.
2. Для Sticky Facts обновить key-value memory с учётом этой реплики **до подготовки основного запроса**. Для извлечения контекста зависимых реплик разрешены предыдущие facts и недавние сообщения; источник и размер входа фиксируются. Сохранять полный актуальный словарь либо явно применять операции изменения/удаления, чтобы не терять неизменённые ключи.
3. Подготовить основной запрос через тот же путь, который используется агентом. Сохранить его для проверки, но в этом тесте не отправлять: ответ ассистента взять из общей фикстуры.
4. Для summary обновлять память по границам завершённых ходов, как при воспроизведении в бенчмарке Дня 9. После 30 сообщений выполнить принудительное сжатие остатка. Все вызовы обновления учесть.
5. Сохранить итоговое состояние стратегии. Для каждого из 13 вопросов восстановить его независимую копию, обработать вопрос обычным путём и получить новый ответ API. Ответы и изменения памяти одной проверки не переносить в следующую.
6. Для Sticky Facts вопрос тоже является пользовательским сообщением: выполнить предусмотренную реализацией обработку обновления facts и учесть дополнительный вызов, если он делается. Обычный вопрос не должен добавлять выдуманное значение в словарь.
7. Оценить 13 ответов, сохранить исходные запросы, ответы, состояния памяти и usage всех обращений к модели.

Если исходный диалог генерируется заново, сначала создать его один раз, сохранить, затем одинаково воспроизвести во всех стратегиях. Расход общей генерации показать отдельно. Смешивать разные исходные ответы ассистента в одном сравнении нельзя.

Ожидания для проверки механики, а не обещания результата модели:

| Стратегия | Итоговый контекст перед вопросом | Что проверяем |
|---|---|---|
| Sliding Window | System + последние 6 сообщений + вопрос | Старые детали отсутствуют; обычно ожидается потеря ранних фактов. Число верных ответов измеряется |
| Sticky Facts | System + актуальные facts + последние 6 сообщений + вопрос | Ранние договорённости сохранены, бюджет обновлён, предложения не превращены в решения |
| Summary | System + summary + хвост + вопрос либо документированный fallback | Память соответствует алгоритму Дня 9; актуальные факты не подменены старыми |

Для Sliding Window нулевой результат по деталям не означает поломку механизма. Для Sticky Facts и summary потери отражаются в качестве памяти и требуют разбора исходных ответов; по одному прогону нельзя гарантировать 13/13 во всех диалогах.

## 5. Тест B: работа живого агента

Цель — убедиться, что стратегии подключены к агенту, а не работают только в отдельной демонстрации.

Для каждой стратегии начать чистый диалог, отправить все 15 реплик Дня 9 и получить реальные ответы. Затем из независимых копий финального состояния задать 13 контрольных вопросов. Сохранить полную трассу. Это отдельный эксперимент: пользовательские реплики одинаковы, ответы ассистента могут различаться.

Проверить оба пути интеграции: `DirectChatAgent → ChatService` и `ToolCallingAgent`. Сейчас оба вызывают `PrepareAsync` с завершённой историей, без текущего сообщения пользователя. Для Sticky Facts потребуется передача текущей реплики либо отдельный шаг обновления перед основным запросом. Тест должен это обнаруживать.

### Проверки механизма без платного API

Использовать настоящий SQLite в памяти и подставной `IAIProvider`, по образцу `Day9CompressionChecks`. Подставной провайдер проверяет построение запросов и хранение; его ответы не использовать как доказательство качества памяти модели.

| ID | Действие | Ожидаемое поведение |
|---|---|---|
| SW-01 | История содержит 4 сообщения, N=6 | Все 4 переданы без перестановок, вызовов поддержки памяти нет |
| SW-02 | История содержит 30 сообщений, N=6 | Переданы только последние 6; ранние тексты, facts и summary отсутствуют |
| SW-03 | Продолжить диалог ещё на 2 сообщения | Окно сдвинулось, его размер ограничен выбранным контрактом |
| SW-04 | Задать N=0, отрицательное или нечисловое значение | Понятная ошибка, настройки не изменены |
| FACT-01 | Сообщить бюджет 480000, затем заменить на 420000 | Единственное актуальное значение бюджета — 420000; обновление выполнено для обеих реплик |
| FACT-02 | Проверить основной запрос сразу после замены бюджета | Он уже содержит обновлённые facts, отставания на один ход нет |
| FACT-03 | Сообщить только новый срок | Остальные факты, включая бюджет и запрет облака, не исчезли |
| FACT-04 | Сказать: «Обсудим облако как идею, офлайн-ограничение не меняем» | Запрет облака сохранён, идея не записана как принятое решение |
| FACT-05 | Спросить: «Какой бюджет?» | Обработчик обновления вызван, если таков контракт; неизвестные значения не придуманы, известные не стёрты |
| FACT-06 | Ошибка API, невалидный JSON, обрезанный ответ или отмена обновления | Предыдущие facts и позиция обработки сохранены; повреждённая память не отправлена как успешное обновление |
| FACT-07 | Повторить обработку уже сохранённой реплики после перезапуска | Данные восстановлены; нет лишнего обновления только из-за загрузки состояния |
| SUM-01 | Запустить существующий `day9 --self-test` | Проверки порога, batch, границ, ошибок, usage и сброса продолжают проходить |
| MODE-01 | Последовательно выбрать Sliding → Sticky → Summary → Sliding | Активный запрос соответствует выбранной стратегии; настройка сохраняется после открытия диалога |
| MODE-02 | При переходе на Sliding ранее существовали facts/summary | Они не отправляются, старые сообщения не восстанавливаются в контекст |
| MODE-03 | Перейти на Sticky/Summary после длинного диалога | Поведение инициализации явно задано: восстановление из архива либо начало памяти с момента переключения; все вызовы инициализации учтены |
| MODE-04 | Задать неизвестное имя стратегии | Понятная ошибка, активный режим не изменён |
| TOOL-01 | Подготовить историю с assistant tool_calls и tool-ответами на границе N | Нет осиротевших tool-ответов или вызовов без результатов |
| RESET-01 | Очистить текущий диалог | История и активная память очищены; состояние соседних веток не изменено |

Для инструментов буквальное обрезание до N может разорвать протокол. До проверки выбрать и описать правило: например, отбрасывать весь ход, пересекающий левую границу, чтобы в завершённой истории осталось не больше N сообщений. Текущий цикл инструментов не обрезать. Если вместо этого сохраняется весь пересекающий границу ход и N становится минимумом, это отклонение от строгого окна нужно показать в отчёте. Основной тест A использует только обычные пары при N=6 и не зависит от этого решения.

## 6. Тест C: checkpoint и независимые ветки

Выполнить для каждой стратегии отдельно. Отсутствие раннего факта в Sliding Window после истечения окна допустимо; появление чужих изменений недопустимо для любой стратегии.

### C1. Создание снимка

После 30 сообщений общего диалога, до контрольных вопросов, сохранить checkpoint `kedr-base`. Снимок содержит доступный журнал/окно, facts или summary с границей обработки, выбранную стратегию, N, batch, системный промпт и настройки модели. Для сравнения состояния записать хеш сериализованного снимка. Расход, уже понесённый до разветвления, хранить как общий префикс.

Создать из одного checkpoint ветки A и B. Создание ветки само по себе не должно требовать генерации модели. Снимок должен оставаться неизменяемым при дальнейшем продолжении исходного диалога и веток.

### C2. Разные продолжения

В ветке A отправить:

```text
Меняем утверждённые договорённости: бюджет теперь 390000 рублей,
срок сдачи — 21 декабря 2026 года, ежедневное напоминание — в 08:45.
Код согласования этой ветки — ЛИПА-47. Остальные решения сохраняются.
Подтверди одним коротким предложением.
```

Переключиться в B и отправить:

```text
Меняем утверждённые договорённости: бюджет теперь 460000 рублей,
срок сдачи — 28 декабря 2026 года, ежедневное напоминание — в 10:15.
Код согласования этой ветки — ИВА-82. Остальные решения сохраняются.
Подтверди одним коротким предложением.
```

Из независимых копий состояния каждой ветки сразу задать четыре вопроса: актуальный бюджет, точный срок с годом, время напоминания, код согласования. Вопросы не должны изменять основную тестируемую ветку.

| Проверка | Checkpoint | A | B |
|---|---|---|---|
| Бюджет | 420000 | 390000 | 460000 |
| Срок | 18 декабря 2026 | 21 декабря 2026 | 28 декабря 2026 |
| Напоминание | 09:30 | 08:45 | 10:15 |
| Код согласования | НЕИЗВЕСТНО | ЛИПА-47 | ИВА-82 |

В самом checkpoint первые три детали могут быть неизвестны при Sliding Window: проверять отсутствие изменений A/B в запросе и неизменность снимка, а не требовать восстановления уже отброшенных данных. Сразу после новых сообщений A/B все четыре новых значения находятся в окне и доступны каждой стратегии.

### C3. Долгое независимое продолжение и переключение

1. В A, затем в B проиграть одинаковые отвлекающие реплики № 9–15 из `Day9CompressionScenario.Messages` с новыми ответами модели: по 14 сообщений. Не повторять бюджет, срок, напоминание и код.
2. Переключаться A → B → A и снова проверить четыре значения из независимых копий текущих состояний. Учесть все обновления памяти. Для summary перед отложенной проверкой выполнить обычное принудительное сжатие, как в тесте A, и записать его стоимость.
3. Для Sticky Facts/summary оценить сохранение значений своей ветки. Для Sliding Window ожидается их вытеснение; уверенные значения чужой ветки считаются утечкой, а не обычной потерей памяти.
4. На уровне хранилища и отправленных запросов проверить: A не содержит продолжения, facts и summary B, и наоборот. Доступный общий префикс совпадает. Повторное переключение само по себе не вызывает модель и не меняет память.
5. Перезапустить приложение/открыть новый DbContext, открыть A и B. Восстановлены выбранная стратегия, свой хвост, своя память и позиции обработки.
6. Открыть исходный checkpoint: его хеш совпадает с исходным. Продолжения веток не дописаны в снимок.
7. Очистить A. История и память B, checkpoint и исходный диалог не изменились.

Все проверки состояния выполнять также с подставной моделью: реальная модель может выдать неверный ответ и без утечки данных. Ответы служат оценкой памяти, снимки и запросы — доказательством изоляции.

## 7. Подсчёт токенов и вызовов

В журнале каждого обращения хранить `run_id`, стратегию, ветку, этап (`dialogue`, `memory`, `probe`), `prompt_tokens`, `completion_tokens`, `total_tokens`, `finish_reason` и время. Для ошибок сохранять попытку и доступный usage; неполный usage обозначать `н/д`, не нулём. Пустые и обрезанные ответы не считать успешным измерением памяти.

Для основного теста A считать:

```text
T_memory = сумма total_tokens всех обновлений памяти при воспроизведении
           + обновления перед независимыми контрольными вопросами
T_probes = сумма total_tokens ответов на 13 контрольных вопросов
T_compare = T_memory + T_probes
Calls_compare = Calls_memory + 13
```

Вход и выход показывать также отдельно. Если API не возвращает `total_tokens`, использовать сумму входа и выхода только при наличии обоих значений. Локальные оценки размера контекста показывать в отдельной колонке, не выдавать их за фактический usage.

Для живого теста B дополнительно показать `T_end_to_end`: все вызовы диалога, памяти и вопросов по каждой стратегии. Эта сумма показывает стоимость полного разговора; `T_compare` теста A показывает стоимость продолжения одинакового диалога. Не складывать две методики в одну строку.

Если Sticky Facts обновляется одним вызовом модели после каждой пользовательской реплики, в тесте A будет 15 вызовов для исходного диалога и ещё 13 при независимых вопросах: 28 вызовов памяти и 13 ответов, всего 41. При детерминированном извлечении вызовов памяти может быть 0, но правило извлечения должно работать с пользовательскими данными, а не содержать эталон «Кедра».

Для Sliding Window поддержка памяти не требует вызовов. Для summary на данном сценарии с N=6, batch=10 и финальным принудительным сжатием ожидаются 3 обновления, как в Дне 9; фактическое число проверить по трассе. Расход теста C выводить отдельно: общий префикс оплатить один раз, продолжения и обновления A/B учитывать раздельно. Копирование накопленных счётчиков в checkpoint не является новым расходом API.
