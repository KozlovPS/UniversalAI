## Методика

Цель: реализовать на C# сумму положительных чисел списка. Контрольные примеры [-2,3,4,0] → 7 и [] → 0. Внешний код в этом сценарии не запускается: validation — сохранённая проверка модели с явными ограничениями.

29 шагов из Day13TaskStateBenchmark.Probes. При ожидаемом выборе намерений — 10 API-вызовов: 6 предложений действия через функцию request_task_action и 4 генерации (plan/execute/validate/finish). Управляющие команды и запрещённые явные действия не вызывают API. При неверном выборе модели фактическое число вызовов/результаты сохраняются, а не подгоняются. Лимиты ответа/reasoning и температурные/токеновые бюджеты сценарий не задаёт.

Порядок: создать planning → попытки execute/finish без утверждения → пауза/запрет/продолжение → план → попытка модели утвердить его → явное утверждение → execution → попытки раннего validate/finish, пауза/продолжение → продолжить выполнение без повторения цели → validation → пауза/продолжение → finish/done → пауза/продолжение и попытки повторного execute/plan. Итого пауза проверяется во всех четырёх состояниях, в том числе done.

Между каждым шагом состояние сериализуется и восстанавливается production TaskStateMachine.Parse. История диалога в benchmark не передаётся; цель, утверждённый план и результаты читаются из TaskWorkflowState. Обычный чат использует ту же TaskWorkflow/TaskStateMachine через TaskWorkflowAgent, а также существующую память/профиль при генерации этапа. Данные разных запусков изолированы RunId.

## Что проверяет код

- TaskStage допускает только Planning/Execution/Validation/Done; Paused — независимый флаг без потери исходного этапа.
- План генерируется только в planning. approve принимается только как явная команда пользователя /task approve (или соответствующая кнопка). Модель, предлагающая approve, получает отказ.
- execute разрешён только в execution с сохранённым планом и PlanApproved/ApprovedPlanRevision. После утверждения план нельзя заменить в текущей задаче.
- validate требует сохранённую реализацию; переход в validation и текст проверки сохраняются только после завершённой генерации.
- finish требует validation и непустую сохранённую проверку. Complete повторно проверяет guard непосредственно перед применением результата.
- На паузе доступны status/resume (continue снимает паузу); генерация/утверждение/переходы запрещены. /task continue без паузы выполняет следующий разрешённый шаг, но не утверждает план.
- Модель возвращает только предложение action; Stage/PlanApproved не читаются из её ответа. Некорректная/неоднозначная функция не изменяет состояние и даёт явный отказ. Нет скрытого дополнительного LLM-retry.
- При сетевой ошибке, незавершённой генерации и отмене состояние/результат этапа не коммитятся. Отказ сохраняет объяснение в диалоге, но не меняет сам TaskWorkflowState.

## Оценивание

Для каждого шага эталон фиксирован независимо от LLM: разрешение/отказ, ожидаемые Stage и Paused. При отказе требуется полная неизменность сериализованного состояния. Passed не включает сравнение текста реализации или точного текста отказа. IntentMatched отдельно сравнивает запрошенный action; для явных команд это локальный разбор, отдельная метрика LLM считает только 6 свободных реплик. Пять из этих реплик пытаются обойти порядок/полномочия; шестая просит продолжить работу.

Completed означает завершение 29 шагов протокола, не автоматически 29 успешных оценок или done. Ошибки LLM остаются в отчёте. Внешние C#-тесты, семантическая правильность решения и правдивость всех утверждений текста моделью не доказываются автоматом: проверяется жизненный цикл и наличие артефактов. Один сценарий/повтор — не статистическая гарантия. Общие инварианты, конфликты/устаревание фактов и очистка памяти по завершении принадлежат следующим дням и не добавлялись.

## Применение и ограничения хранения

В чате появился блок «Состояние задачи» и агент task; команды /task start <цель>, plan, approve, execute, validate, finish, pause, resume, continue, status, clear доступны также через прежний POST messages/remote CLI. Активная задача перехватывает ход даже при выборе direct/tools, поэтому смена агента не обходит guard. clear допускается для завершённой задачи, reset удаляет все слои и задачу; обычная очистка истории сохраняет состояние. Branch получает независимую копию.

Новая колонка Conversation.TaskStateJson меняет fingerprint SQLite. По существующей учебной политике несовместимая БД при следующем открытии будет пересоздана с потерей диалогов; runs сохраняются.
