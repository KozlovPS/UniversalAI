В чате выбрать «Обновляемая память» в настройках ответов, в CLI — /agent evolving. Записи явные, автоматического извлечения из свободной речи нет:

```text
/remember {"Key":"deadline","Value":"2026-12-20","Policy":"replace"}
/remember {"Key":"decisions","Value":"Принят модульный монолит","Policy":"append"}
/remember {"Key":"temporary","Value":"Черновик задачи","Policy":"task"}
/remember list
/remember audit
/remember complete
```

WrittenAt необязателен: сервер назначает UTC-время записи. Для запоздавшего события можно передать ISO timestamp. replace/task принимают только строго более позднюю запись; при равенстве остаётся прежнее значение. Политика существующего ключа не меняется. append накапливает уникальные значения с индивидуальным временем и сортирует по времени. История изменений может храниться отдельным append-ключом; аудит всех замен ведётся автоматически с before/after/временем.

complete удаляет временные факты и рабочую память, сохраняет текущие долговременные факты, списки и audit. Переход штатного FSM в Done тоже выполняет очистку. Полный reset удаляет обновляемую память. Отдельное EvolvingMemoryJson сохраняется в SQLite и независимо копируется в ветку. Прежние FactsJson автоматически не переносятся.

В модель передаются инструкции памяти, актуальные факты/списки/временные данные, рабочая память и текущий вопрос. История и audit доступны для просмотра, но не входят в промпт. Рабочие ключи, совпадающие с ключами обновляемой памяти, исключаются из запроса. При task-модуле и выбранном evolving общий ContextCompressionService также использует актуальный контекст. Инварианты сохраняют приоритет. Это отдельный явно выбираемый агент; поведение обычного прямого чата не меняется.

## Методика: scenario v2 / scorer v1

Один диалог, 26 последовательных наблюдений: 13 локальных операций + 13 API-ответов. Веб отдельно считает агрегатную проверку сохранности слоёв: 27/27 при полном успехе.

1. По очереди записать deadline=2026-12-01, requirement=EXPORT_REQUIRED, approach=MICROSERVICES, version=VERSION_1. После каждой записи задать вопрос.
2. По очереди заменить на 2026-12-20, EXPORT_CANCELLED, MODULAR_MONOLITH, VERSION_2. После каждой замены проверить ответ и отсутствие уже заменённых значений во всех сообщениях запроса.
3. Запоздавшая запись старой даты не должна заменить актуальную. Повторить вопрос.
4. Накопить DECISION_A и DECISION_B списком; запросить оба значения.
5. Создать временный TASK_ONLY; рабочий слой содержит WORKING_ONLY. Завершить задачу, проверить пустоту рабочего/временного слоя и точное сохранение долговременных фактов/списков.
6. Вопросы temporary/scratch → НЕИЗВЕСТНО; deadline → актуальная дата. Удалённые/заменённые контрольные значения отсутствуют в полном промпте.

Эталоны независимы от ответа. Оценка — точное регистронезависимое сравнение после удаления внешней пунктуации. Счётчик устаревших ответов ищет прежние контрольные значения, счётчик утечек — те же значения во всех сообщениях запроса. Это лексическая проверка фиксированного сценария. Списки намеренно сохраняют прошлые решения. Модель отвечает свободным текстом; ошибочные ответы сохраняются и учитываются. Протокол Completed не равен хорошему качеству.

В журнале показаны план, модель, число запросов, операции, состав контекста, before/after, эталон, ответ и оценка. experiment-view.json даёт этапы/инспектор и просмотр сохранённого процесса. Журнал открывается первым; итоговая вкладка показывает сохранённые оценки и вывод.
