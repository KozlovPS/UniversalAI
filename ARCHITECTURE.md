# Архитектура UniversalAI

## Проекты и зависимости

```text
UniversalAI.csproj (CLI) ──────┐
                             ├── UniversalAI.Benchmarks ── UniversalAI.Engine
UniversalAI.Web (Blazor/API) ─┘

UniversalAI.Checks ────────────── Engine + Benchmarks
```

Корневой проект оставлен консольным для совместимости с `dotnet run -- --benchmark dayN`. Исходники ядра находятся в `src/UniversalAI.Engine`, эксперименты — в `src/UniversalAI.Benchmarks`. Новые интерфейсы не зависят от консольных классов.

## Общее ядро

- `Core/`: запросы, сообщения, результаты, возможности моделей, проверка протокола.
- `Providers/`: реализация GigaChat и OpenAI-compatible. Профили облачных и локальных серверов задаются конфигурацией. Для неизвестной модели нужен явный профиль возможностей; параметры не угадываются по имени.
- `Services/Agents/`: `IAgent`, реестр, прямой чат и цикл инструментов. Новый агент регистрируется через DI.
- `Services/WorkspaceService`: операции приложения для CLI, API и Blazor. Для каждой операции создаёт отдельный scope и DbContext. EF-сущности не уходят в интерфейсы; наружу возвращаются DTO.
- `Services/ConversationGate`: сериализует весь ход одного диалога, его настройки, очистку и создание ветки. Разные диалоги могут выполняться независимо. Блокировка действует в одном процессе; `StorageLease` предотвращает запуск двух владельцев одного каталога.
- `Services/ConversationService`: хранение сообщений, настроек, summary и facts. Сообщения успешного хода сохраняются одной транзакцией. Новые Sticky Facts сохраняются с успешным ходом; ошибка основного ответа не должна менять факты диалога.
- `Services/IContextMemoryStore`: отделяет алгоритм summary от SQLite. Day-10 использует хранилище snapshot в памяти без создания временной базы на каждом запросе.
- `Configuration/`: пути данных, DI, профили и версионируемый каталог тарифов.

`ProviderFactory` использует `IHttpClientFactory`. Экземпляры GigaChat переиспользуются вместе с синхронизированным кэшем OAuth-токена. Конфигурация и метаданные содержат имя переменной ключа, а не значение ключа.

## Память

В обычном чате обе реализации агента используют выбранную в диалоге стратегию:

- `Summary`: накопительное сжатие по исходным границам Day-9, полный журнал остаётся в БД.
- `SlidingWindow`: отбор последних сообщений с соблюдением целостности tool-ходов.
- `StickyFacts`: обновление фактов до запроса ответа; новые факты используются в контексте и фиксируются при успешном сохранении хода.

Отключение памяти возвращает полную историю. Переключение стратегии не удаляет архив, прежнее summary и facts. При первом включении facts извлечение использует текущую реплику и недавний контекст; отдельный ретроспективный пересчёт всего архива не выполняется. `/reset` очищает журнал и память. Usage поддержки памяти показывается отдельно от ответов.

## Эксперименты

`IBenchmark` принимает `BenchmarkSettings` и `BenchmarkExecutionContext`; он не зависит от HTTP или жизненного цикла страницы. Реестр получает реализации из DI, поэтому следующие задания добавляются отдельными модулями.

Day-3/4/5/9/10 имеют типизированные `ExecuteAsync`; прежние `RunAsync(string[])` остаются адаптерами справки, self-test, rescore и совместимых запусков. Наборы задач, порядок вызовов и оценивание сохранены.

`BenchmarkOutput` — адаптер представления для существующих протоколов. Его контекст привязан к async-выполнению; он не переназначает `Console.Out`. Новый модуль может работать напрямую с `context.Output` и `context.CreateProvider()`.

`BenchmarkRunner` фиксирует настройки и endpoint, сохраняет состояние, тарифы и все попытки API. `FileRunStore` хранит метаданные вне рабочей SQLite. Каждый RunId — GUID; артефакты доступны только по проверенным именам внутри каталога запуска.

`BenchmarkQueue` выполняет серверные задания последовательно с ограниченной очередью. Закрытие браузера не отменяет прогон. Отмена — отдельная операция. После остановки процесса незавершённые задания становятся Interrupted; автоматический повтор сетевых запросов отсутствует. Частичные результаты и ошибки остаются доступными.

`RunMetricsReader` читает журнал вызовов и использованный снимок тарифов. Отсутствующие usage/тарифы остаются Н/д. Общая метрика всего запуска не подменяет методические таблицы Day-9/10.

## Интерфейсы

CLI работает через `IWorkspaceClient`: локальный `WorkspaceService` либо `RemoteWorkspaceClient`. Обработчик консольных команд разбирает текст и вызывает общие операции.

Blazor Interactive Server обращается к тем же операциям напрямую. API предоставляет их удалённой консоли и будущим клиентам. Компоненты не держат DbContext. Выполнение бенчмарков принадлежит hosted service, а не компоненту или HTTP-запросу.

Веб рассчитан на одного владельца рабочего пространства с нескольких устройств. Без токена принимается только loopback; при заданном токене используются Bearer для API и cookie для браузера. Для публикации нужен HTTPS. Раздельные пользователи и права на отдельные данные — будущая задача.

## Хранение и учебная схема

`UNIVERSALAI_DATA_DIR` определяет корень БД, ключей веб-сессий и файлов прогонов. Каталог не зависит от текущей директории. `DatabaseInitializer` сравнивает отпечаток схемы и пересоздаёт несовместимую учебную БД. Миграции не реализованы по выбранному ограничению проекта.

SQLite используется одним процессом, с WAL и короткими транзакциями записи. Сетевые вызовы модели выполняются вне транзакций БД. При необходимости нескольких серверных процессов потребуются другое согласование очереди/ходов и оценка перехода на PostgreSQL.
